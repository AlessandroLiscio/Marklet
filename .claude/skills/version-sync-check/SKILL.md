# Version sync check

Reports whether release bookkeeping is consistent. **It changes nothing.** No file is
written, no tag is created. That is what makes it safe to run before anything else, and it
is why the `release` skill calls it as its first real step.

## What is compared

`.github/RELEASE_TARGETS.yml` declares the write targets. This audit reads them and compares
four things:

| Source | How to read it |
|---|---|
| `package.json` | `node -p "require('./package.json').version"` |
| `src-tauri/Cargo.toml` | the `^version = ` line in the `[package]` section |
| `src-tauri/tauri.conf.json` | `node -p "require('./src-tauri/tauri.conf.json').version"` |
| Newest dated changelog section | the first `## [X.Y.Z] — YYYY-MM-DD` in `CHANGELOG.md` |
| Newest git tag | `git tag -l 'v[0-9]*' --sort=-v:refname \| head -1` |

```bash
git fetch --tags
```

Fetch first. The audit reads local tags only, and unfetched it answers the newest-tag
question from stale data — which is exactly the question that matters most.

**`-l 'v[0-9]*'` is required, not cosmetic.** Repositories accumulate non-semver tags. An
unfiltered `git tag | head -1` picks lexically and will happily return `latest` or a vendor
tag as if it were a version.

## The verdicts

Report exactly one, and say which comparison produced it.

**In sync** — all three version files agree, and they match the newest tag.

**Bookkeeping ahead of the tag** — the three files agree with each other and with the newest
dated changelog section, but no tag exists for it. This is the normal state between "release
prepared" and "release cut", and it is the one case the `release` skill handles by skipping
straight to tagging. Not drift.

**Drift** — any disagreement among the three version files, or between them and the newest
dated changelog section. Name every file and its value; do not summarise. A release cut on
top of unresolved drift bakes the problem into the release.

**Config broken** — a path declared in `RELEASE_TARGETS.yml` does not exist, or its `match`
anchor no longer finds a line. Report which. This usually means a file moved and the config
did not follow, and it means the next release would silently skip that file.

**Never released** — no tag matching `v[0-9]*` exists. Say so plainly; it changes what the
next release means. Marklet is in this state until v0.1.0 is tagged.

## What is deliberately not compared

`.github/RELEASE_TARGETS.yml` lists four locations under `never_touch`. Do not read them as
version sources and do not report them as drift:

- **`src-tauri/Cargo.lock`** carries `name = "marklet"` followed by a `version` line, which
  looks exactly like a write target. It is generated from `Cargo.toml` by `cargo build`.
- **`package-lock.json`** carries the version twice, plus every dependency's pinned version.
  Generated by npm.
- **`src-tauri/tauri.conf.json`'s `$schema`** pins Tauri's config schema, not the app.
- **`docs/size-budget.md`** records measured sizes per release. Those are historical
  measurements.

If one of the two lock files disagrees with its manifest, that is worth mentioning as an
aside — it means someone hand-edited a lock or forgot to rebuild — but it is not drift in the
sense this audit gates on.

## Reporting

Lead with the verdict. Then a table of every source and its value, so the reader can see the
disagreement rather than take your word for it. Then, only if the verdict is Drift or Config
broken, what would need to change.

Do not propose a next version number. That is the `release` skill's Step 1, and it needs a
human decision this audit is not equipped to make.
