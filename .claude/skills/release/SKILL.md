# Release

## Versioning

Semver. **The release is the tag, not a version file.** The tag is what a consumer resolves;
everything before it is bookkeeping that has to be correct first.

CURRENT comes from the newest tag, never from a version file:

```bash
git fetch --tags
git tag -l 'v[0-9]*' --sort=-v:refname | head -1
```

The `-l 'v[0-9]*'` filter is required, not cosmetic — an unfiltered `git tag | head -1` picks
lexically and will return `latest` or a vendor tag as if it were a version. No matching tag
means this repository has never been released; say that out loud, because it changes the
conversation.

**`.github/RELEASE_TARGETS.yml` declares which files a release moves.** Read it; do not
guess and never `grep -r` the version string and bulk-replace. That file also lists four
`never_touch` locations, each of which looks exactly like a write target:

| Looks like a target | Actually |
|---|---|
| `src-tauri/Cargo.lock` | generated from `Cargo.toml` by `cargo build` |
| `package-lock.json` | generated by npm; carries the version twice plus every dependency's |
| `tauri.conf.json` `$schema` | pins Tauri's config schema, not the app |
| `docs/size-budget.md` | historical per-release measurements |

Edit each declared file **in place, one line at a time**: re-read the line, confirm it still
holds the old value, write only that line. Never round-trip a manifest through a JSON or TOML
parser — it reformats everything else in the file.

`.github/workflows/release.yml` verifies the three declared files agree with the tag and
fails the release if they do not.

## Audit before you write

Run the read-only `version-sync-check` skill first and read its verdict. **Any verdict other
than "in sync" or "bookkeeping ahead of the tag" stops the release** until it is resolved
with Alessandro. A release cut on top of unresolved drift bakes the problem into the release.

"Bookkeeping ahead of the tag" is the one case that skips work rather than adding it: the
version files and changelog were already written and only the tag is missing, so go straight
to tagging.

## What a tag produces

Pushing `v*` runs `release.yml`, which builds on `windows-latest` and `ubuntu-22.04`:

| Artifact | Build | Notes |
|---|---|---|
| `marklet-setup.exe` | default features | full, includes Mermaid |
| `marklet-lite-setup.exe` | `--no-default-features` | ~750 KB smaller, no Mermaid |
| `marklet-offline-setup.exe` | `webviewInstallMode: offlineInstaller` | ~127 MB, air-gapped machines only |
| `marklet-<ver>.AppImage` | default | Linux |
| `marklet-<ver>.deb` | default | Linux |
| `SHA256SUMS` | — | covers every artifact above |

The offline installer is built **only** on tags. It is 127 MB because it embeds the whole
WebView2 runtime; it must never become the default download.

## The size gate runs first

`size-gate.yml` fails the release if either primary installer is over budget:

| Artifact | Ceiling |
|---|---|
| `marklet-setup.exe` | 3\_670\_016 B |
| `marklet-lite-setup.exe` | 2\_936\_013 B |

A release is not cut over a failing size gate. Cut the feature or ship the previous version.
See `.claude/skills/size-budget/SKILL.md`.

## Cold-start gate

Five runs of `marklet --benchmark tests/fixtures/large.md` on `windows-latest`; the median
`boot-ms` must be under 1200 ms. This is the promise the whole project rests on, so it gates
the release rather than merely reporting.

## Changelog

`CHANGELOG.md`, Keep a Changelog format, newest first. Every entry says what a user can now
do, not which file changed. Size and cold-start deltas against the previous release go in
the entry — users of a "lightweight" tool care about that number, and publishing it keeps us
honest.

## Checklist

1. Run `version-sync-check`. Resolve anything it reports before writing.
2. `CHANGELOG.md` updated: `## [Unreleased]` becomes `## [X.Y.Z] — YYYY-MM-DD`, em-dash and
   ISO date, with a fresh empty `## [Unreleased]` left above it. Match the existing category
   style; never impose one.
3. Version bumped in every file `.github/RELEASE_TARGETS.yml` declares, and nothing outside
   it. All of them or none — a repository whose version files disagree after a release is
   worse than one that was never released.
4. `cargo test`, `npm test`, `cargo clippy -- -D warnings` green on `main`.
5. Show the full `git diff` and the proposed tag name, then **stop and wait for approval**.
6. `git tag -a vX.Y.Z -m "…" && git push origin vX.Y.Z`. **The tag push is the release** —
   `release.yml` triggers on it. Watch the run and report its real result; do not call the
   release done because the push succeeded.
7. Verify the artifact sizes in the run summary against the previous release.
8. Download `marklet-setup.exe` on a real Windows 11 machine, install it, double-click a
   `.md` file, uninstall it, then confirm `reg query HKCU\Software\Classes /f marklet /s`
   returns nothing. Only then publish the draft release.

Step 8 is not skippable, and it is why the release is created as a draft. CI cannot test the
Explorer double-click path, and that path is the product.
